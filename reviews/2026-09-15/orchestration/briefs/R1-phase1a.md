## Part 1 — PLAN 1.1: vendor the pinned Unicode Character Database files

Claim the beads issue for plan item 1.1. Law 1 applies directly: this task
creates the ground truth that every later Unicode task cites.

### Files

Vendor exactly these files, from the official Unicode 17.0.0 locations,
under `reference/unicode/17.0.0/`. Keep the upstream relative paths:

- `ucd/EastAsianWidth.txt`
- `ucd/emoji/emoji-data.txt`
- `ucd/auxiliary/GraphemeBreakProperty.txt`
- `ucd/auxiliary/GraphemeBreakTest.txt`
- `ucd/DerivedCoreProperties.txt`. This contains the `InCB` property needed for
  GB9c and `Default_Ignorable_Code_Point`. Verify that InCB is really in this
  file for 17.0.0; if it is somewhere else, vendor that file and say so.
- `ucd/extracted/DerivedGeneralCategory.txt`
- `emoji/17.0/emoji-test.txt`. Find the correct official URL for emoji-test at
  Unicode 17 / Emoji 17.0 by checking unicode.org's directory listings; do not
  guess.

Rules for the vendoring:

- Check that each file's header states version 17.0.0 (or Emoji 17.0), and
  record the first header lines in your report.
- Do not modify the files.
- Check the licence: the Unicode data files are under the Unicode License v3.
  Vendor the licence text, fetched from unicode.org, as
  `reference/unicode/LICENSE` (or put it under the version directory if that
  fits better). Add a short `reference/unicode/README.md` covering what is
  vendored, from where, under what licence, the pinned version, and how to
  refresh the files.

### Integrity and refresh

1. **`reference/unicode/17.0.0/SHA256SUMS`**, in `sha256sum -c`-compatible
   format with paths relative to that directory.
2. **Fetch script:** a babashka script at `scripts/fetch-ucd.clj` (or a bb task
   `bb fetch-ucd`). It takes the version, downloads into a temporary directory,
   verifies against `SHA256SUMS` when one exists, refuses to overwrite on any
   mismatch, and prints what it did. It never runs as part of `bb check`,
   because no network access happens in tests.
3. **Integrity test:** a test in `bb check` that recomputes the SHA-256 of
   every vendored file and compares it with `SHA256SUMS`, on both runtimes.
   Red first: run it before `SHA256SUMS` exists, or against a deliberately
   wrong checksum, and see it fail.
4. **Line endings:** add a `.gitattributes` entry so these files are never
   normalised, e.g. `reference/** -text`. This keeps the checksums stable
   across platforms.

### Scope

Do not write generators, tables or segmentation code; that is 1.2 onward. Do
not touch `src/`.

In your report, give the total size of what was vendored. If
`GraphemeBreakTest.txt` plus the others exceeds a few MB, that is fine; just
report it.

Verify: `bb check` passes. Report the counts.

## Part 2 — PLAN 1.2: deterministic Unicode property table generator

Claim the beads issue for plan item 1.2. Ground truth is the vendored data under `reference/unicode/17.0.0/`, which part 1 added. Verify it exists, and check its `SHA256SUMS` before you start.

### What to build

1. **A generator script.** Write it as `scripts/gen-unicode-tables.clj`, runnable as `bb gen-unicode`.
   - It reads the vendored UCD files and writes `src/limner/unicode/tables.clj`.
   - That output is a namespace with an AUTOGENERATED banner. The banner names the Unicode version, the source file paths, and their SHA-256s (read from `SHA256SUMS`), and says "do not edit; run `bb gen-unicode`".
   - The generator is deterministic and byte-stable: sorted output, no timestamps, stable formatting.

2. **The tables.** For each property, emit compact, merged, sorted ranges as `[start end value]` triples. Use a flat primitive encoding if that loads faster; measure both on bb before choosing. The later tasks need these properties:
   - `East_Asian_Width` (all classes; the unlisted default is N, per the file's header).
   - `Grapheme_Cluster_Break` (all values; the default is Other).
   - `Extended_Pictographic` (from `emoji-data.txt`).
   - `Emoji_Presentation` (from `emoji-data.txt`).
   - `Default_Ignorable_Code_Point` (from `DerivedCoreProperties.txt`).
   - `InCB` (`Indic_Conjunct_Break`: Linker / Consonant / Extend, from `DerivedCoreProperties.txt`; confirm where part 1 found it).
   - `General_Category` (from `extracted/DerivedGeneralCategory.txt`). Emit either all categories, or only the subset the width rules need (Mn, Me, Mc, Cf, Cc, Zl, Zp, Cs, Co, Cn). Justify the choice in the namespace docstring. Smaller is better if later tasks only need the subset: look at PLAN D3 and the width semantics to decide.
   - Handle `@missing` default lines correctly. The 17.0 files use `# @missing:` lines to declare defaults, and they matter (for example the EAW default for unassigned CJK ranges is W, not N). Parse them and apply them as the file header specifies. Get this right against the file itself, not memory.

3. **A lookup namespace, `limner.unicode`.** Public functions:
   - `version` returns `"17.0.0"`.
   - Property lookups by code point: `east-asian-width`, `grapheme-break`, `extended-pictographic?`, `emoji-presentation?`, `default-ignorable?`, `incb`, `general-category`.
   - Lookups use binary search over the ranges and must run in constant memory.
   - Lookups throw `ex-info` for inputs outside 0..0x10FFFF. That is fail-loud behaviour (Rule 1).
   - Write a literate namespace docstring (Rule 10) covering what the data is, which version it comes from, how defaults work, and why the tables are generated.

   Do not implement width or segmentation rules here. Those are 1.3 and 1.4.

### Tests

Write these red first.

- **Drift test.** Regenerate into memory or a temp file and compare byte-for-byte with the committed `tables.clj`. It fails if someone edits the tables by hand or changes the UCD files without regenerating. It must run on both runtimes.
- **Spot tests against the raw data.** For a few hundred code points sampled deterministically (fixed seed) across all planes, parse the raw UCD line for that code point directly in the test (an independent simple parser, not the generator's code path) and compare it with the lookup. Include the edge cases:
  - `@missing` defaults
  - U+10FFFF
  - surrogates
  - private use
  - unassigned code points in the CJK blocks
- **Exact checks** for a few property values we already know from REVIEW C1/C2:
  - EAW: U+3000 W, U+2630 W, U+2713 N, U+1F170 A.
  - Emoji_Presentation: U+26A1 true, U+2764 false.
  - Default_Ignorable: U+00AD true, U+FEFF true.
  - GCB: U+200D ZWJ, U+1F1E6 Regional_Indicator.
  - One InCB Linker, for example U+094D.
- **Mutation-prove.** Edit one generated range by hand, confirm the drift test and at least one spot test go red, then restore.

### Performance

Report the following on both JVM and bb:

- namespace load time
- lookup throughput (lookups/s over a fixed corpus)
- size of `tables.clj`

If the generated source is too large to load fast on bb (for example over 1 s), choose a more compact encoding, such as delta-encoded strings decoded at load time. Justify the choice in the docstring. Put the measured numbers in the bead.

`bb check` must pass. Report the counts.

## Part 3 — PLAN 1.3: ADR 0001 on terminal width semantics, plus the width functions it defines

Claim the beads issue for plan item 1.3. Your inputs are the lookups from
`limner.unicode` (part 2) and the vendored UCD 17.0.0 data.

### 1. Research, reading only the primary sources

- **UAX #11 (East Asian Width).** Fetch the text of the version matching
  Unicode 17 from unicode.org. Read what it says about ambiguous width,
  and its recommendation that East_Asian_Width must not be applied
  blindly.
- **UTS #51 (Emoji).** Read the sections on emoji presentation, VS15 and
  VS16, and on RI flag sequences.
- **Existing implementations**, to know where the ecosystem stands. You
  are surveying, not copying:
  - Python `wcwidth` (jquast), in particular its `wcswidth` and its
    zero-width and VS16 handling. Read the source from its GitHub repo
    with curl.
  - glibc's `wcwidth` behaviour. The table pmonks posted is in
    `reviews/2026-09-15/evidence/glibc-wcwidth-U2600-U27BF.tsv`.
  - Markus Kuhn's `wcwidth.c` rules.
- Save the upstream texts you actually used under `reference/specs/`
  (UAX #11 and UTS #51, HTML or text), with their URLs and SHA-256s in a
  README, so that the ADR can cite local paths (Law 1). Check licence
  compatibility: Unicode technical reports are under the Unicode terms of
  use, so note that. Do not vendor wcwidth source code; cite it by URL
  and commit hash.

### 2. Write `docs/adr/0001-terminal-width-semantics.md`

Structure: Context / Decision / Consequences / Alternatives considered /
References.

The decision must be expressed only in terms of UCD properties, so that it
is testable. Starting points (PLAN D3), which you must justify or amend
from the sources:

- **Code point width**
  - C0/C1 controls (Cc) other than those listed below: decide between
    width 0, an error, or leaving them to the caller. Consider what callers
    of `visible-width` need: newlines and tabs appear in real text. The
    recommended starting point is width 0 for Cc, with documentation that
    layout functions reject or handle `\n` and `\t` explicitly (a bead for
    Phase 3). Justify whatever you pick.
  - `Default_Ignorable_Code_Point` → 0.
  - General categories Mn, Me → 0. Decide Mc explicitly: spacing marks are
    usually width 1 in terminals, but check what wcwidth does, and give
    reasons.
  - Cf → 0, except for any exceptions you find (for example U+00AD SOFT
    HYPHEN: check the `wcwidth` precedent).
  - Hangul Jamo medial and final (GCB V and T) → 0 inside a cluster.
  - East_Asian_Width W or F → 2.
  - East_Asian_Width A → 1 by default. There is an explicit option for 2.
    Its API shape is either a dynamic var or an options map; pick one and
    justify it against CLAUDE.md Rule 7 (pure core, injectable).
  - Everything else → 1.
  - Surrogates, unassigned code points and noncharacters: decide and
    justify.
- **Grapheme cluster width**
  - The base width, with adjustments.
  - VS16 (U+FE0F) following an emoji base → 2.
  - VS15 (U+FE0E) → text presentation, width per EAW.
  - An RI pair → 2; a lone RI → 1 (EAW N). Say what the Emoji
    specification and terminals do.
  - Emoji modifier sequences and ZWJ sequences → 2.
  - Keycap sequences → 2.
  - A cluster whose base is zero-width (for example a leading combining
    mark) → the width of its first non-zero code point, or 1. Choose and
    justify.
- **Version skew.** Say plainly that terminals and libcs lag the standard
  (Yijing example: U+2630–2637 and U+268A–268F are W in Unicode 16+ but
  glibc reports 1), and that limner follows the pinned UCD version, which
  is exposed as data.
- **Out of scope:** tabs and cursor-position-dependent width.

### 3. Implement `limner.unicode.width`

The ADR is the specification.

- `code-point-width` takes a code point and an options map.
- `cluster-width` takes a string that the caller asserts is one grapheme
  cluster, plus options. It does not segment; segmentation is the 1.4 bead (next run).
- Write the namespace docstring as a chapter that follows the ADR and
  cites it.

### Tests, red first

- An exhaustive test over all code points 0..0x10FFFF, comparing
  `code-point-width` against an independent restatement of the ADR rules
  written directly from the raw UCD files inside the test. It must be
  fast enough for the suite: measure it, and if it is too slow on bb, run
  every code point on the JVM and a deterministic sample of at least 50k
  on bb, and document that split.
- Exact tests for every example in the ADR and every C1 probe in
  `reviews/2026-09-15/evidence/probe.clj`: U+3000, U+3001, U+3131, U+3220,
  U+338F, U+1F170, U+1F321, U+00AD, U+2060, U+FEFF, and a lone RI.
- `cluster-width` tests for ❤️ (U+2764 U+FE0F), ❤︎ (U+2764 U+FE0E),
  🇩🇪, 👍🏽, 👨‍👩‍👧‍👦, the keycap 1️⃣, e + U+0301, and a Hangul L+V+T jamo
  sequence.
- The ambiguous-width option: U+2605 ★ is 1 by default and 2 with the
  option.
- Mutation-prove: flip the A rule and the VS16 rule one at a time, confirm
  the tests go red, and restore.

Do not change `limner.core/visible-width` yet; the 1.6 bead (a later run) will switch it
over. Put the glibc and Python `wcwidth` comparison into 1.7. Here, only
note in the ADR where our choices differ from those two and why.

`bb check` must pass. Report the counts.
